# Seed and demo data

- **Situation:** "seed the database", reference data (roles, permissions, currencies, chart of accounts), demo or sample data for sales and tests, default data for each new tenant on signup, "seed ran twice and duplicated".
- **Skip when:** the schema needs no starting rows and tests build their own fixtures.
- **Decision:** three kinds of seed, kept apart: reference data (runs in every environment, idempotent, versioned), demo data (never in production, clearly fake), tenant defaults (created inside the signup transaction). Every seed is safe to run twice.

## Levels

| Level | Pick when |
|---|---|
| Minimum | Small app: idempotent reference seed, a dev-only demo seed, a production guard |
| Standard | SaaS: + per-tenant defaults on signup, seeded ids, reference data updated by migrations, seed tests |
| Advanced | Many tenants and plans: versioned defaults rolled out to existing tenants, deterministic large datasets for load tests |

## Rules

### Minimum — always, never cut

- Three folders and three commands: `seed:reference` (all environments), `seed:demo` (dev, staging, demo only), `seed:tenant` (called by code). They never import each other's data.
- Every seed is idempotent: natural or fixed key plus `INSERT … ON CONFLICT (…) DO UPDATE` (or `DO NOTHING` when owners may edit the row). Running twice changes nothing.
- Reference rows use fixed ids or unique codes written in the seed (`Code: "Orders.Refund"`, a constant uuid for system roles); never `gen_random_uuid()` for something other rows refer to by name.
- `seed:demo` refuses to run when `NODE_ENV=production` or when the database host is not on an allow-list, and prints which database it is about to touch.
- Never seed real-looking personal data: no real names with real phone numbers, no real national ids or cards. Emails use a reserved domain (`@example.com`), phones use a non-routable test range, ids and cards follow documented test values, names are generated and obviously fake.
- Never ship a default admin password. A first admin is created from an environment variable or a one-time setup link, and the password is forced to change.
- Seeds go through the same validation and constraints as the app; they never disable foreign keys or triggers.

### Standard — adds

- Reference data that code depends on (roles, permissions, tax rates such as VAT 14%, statuses) is applied on every deploy by `seed:reference`, after migrations, in a transaction, and removing a row is a migration, not a seed edit (`backend/data/migrations.md`).
- Tenant defaults (settings, chart of accounts, default warehouse, roles, a sample category) are created by one `CreateTenant` function in the **same transaction** as the tenant, owner user and membership. A failure leaves no tenant (`backend/data/multi-tenancy.md`).
- Tenant defaults are copied from templates, not referenced, so a tenant can edit theirs without touching others; the `DefaultsVersion` applied is stored on the tenant.
- Demo data is generated with a seeded PRNG (fixed seed) so it is the same every run, includes boundary cases (zero, long names, Arabic and English, soft-deleted rows, an end-of-month order near midnight in `Africa/Cairo`), and money in integer piasters (`backend/data/money.md`).
- Seeds run in CI against a fresh database, twice, and the second run must report zero changes.
- Demo tenants are flagged (`IsDemo`) and excluded from billing, emails and analytics; outbound emails and SMS from demo are blocked.

### Advanced — adds

- When defaults change, a versioned job upgrades existing tenants in batches: adds missing rows, never overwrites tenant edits, records the new `DefaultsVersion` (`backend/reliability/background-jobs.md`).
- Load-test datasets of 100× volume generated by `COPY` or batched inserts, in a separate database, never restored from production.
- Demo reset: a job recreates the demo tenant nightly in one transaction per tenant.

## Edge cases

| Case | Expected behaviour |
|---|---|
| Seed run twice, or two deploys seed at once | Second run changes nothing; a Postgres advisory lock lets only one process seed |
| Tenant owner renamed a default role, then reference seed reruns | Tenant copies untouched; only system reference rows are updated |
| Signup fails after the tenant row is inserted | Whole transaction rolls back; no half tenant, email stays free to retry |
| Two signups with the same slug in parallel | Unique `(Slug)` makes one fail with `409`; defaults are never created twice |
| Production accidentally pointed at by `seed:demo` | Refuses before connecting to write; requires host allow-list match |
| Seed references a row an old production database lacks | Seed creates it first inside the same transaction, or fails clearly; never silent skip |
| Demo order dated on the 31st at 23:30 Cairo time | Stored in UTC; reports for the Cairo month still place it correctly (`backend/data/time-zones.md`) |
| Unique constraint added later while old seeds duplicate rows | Migration cleans duplicates first; seed keys are fixed so no new duplicates appear |
| 100×: 10,000 signups a day, 200 default rows each | Defaults inserted with one multi-row `INSERT` per table, not per-row loops; template rows cached in memory |
| Twice / parallel: same seed from two CI jobs against one database | Advisory lock plus `ON CONFLICT`; final counts equal one run |

## Example — Standard, Bun + Hono + Drizzle

```ts
export async function SeedReference() {
  await db.transaction(async (Tx) => {
    await Tx.execute(sql`SELECT pg_advisory_xact_lock(724001)`)
    await Tx.insert(Permissions).values(PERMISSIONS.map((Code) => ({ Code })))
      .onConflictDoNothing({ target: Permissions.Code })
    await Tx.insert(Roles).values(SystemRoles)
      .onConflictDoUpdate({ target: Roles.Id, set: { Name: sql`excluded."Name"` } })
    await Tx.insert(TaxRates).values({ Id: VatId, Code: "VAT", RateBasisPoints: 1400 })
      .onConflictDoUpdate({ target: TaxRates.Id, set: { RateBasisPoints: sql`excluded."RateBasisPoints"` } })
  })
}

export async function CreateTenant(Input: TSignupInput) {
  return db.transaction(async (Tx) => {
    const [Tenant] = await Tx.insert(Tenants).values({ Name: Input.Name, Slug: Input.Slug, DefaultsVersion: CurrentDefaultsVersion }).returning()
    const [Owner] = await Tx.insert(Users).values({ Email: Input.Email, PasswordHash: await HashPassword(Input.Password) })
      .onConflictDoNothing({ target: Users.Email }).returning()
    if (!Owner) throw new AppError("EMAIL_TAKEN", 409)
    await Tx.insert(Memberships).values({ TenantId: Tenant.Id, UserId: Owner.Id, Role: "Owner" })
    await Tx.insert(Warehouses).values({ TenantId: Tenant.Id, Name: "Main", IsDefault: true })
    await Tx.insert(Accounts).values(DefaultAccounts.map((A) => ({ ...A, TenantId: Tenant.Id })))
    return Tenant
  })
}

export function AssertDemoAllowed(DatabaseUrl: string) {
  const Host = new URL(DatabaseUrl).hostname
  if (Bun.env.NODE_ENV === "production" || !DemoHosts.includes(Host)) throw new Error(`Demo seed refused for ${Host}`)
  console.log(`Seeding demo data into ${Host}`)
}
```

`CreateTenant` is the only place defaults are made, so signup, an admin-created tenant and tests all get the same rows or none. If the user already exists, signup becomes "create tenant for the signed-in user" instead of the `EMAIL_TAKEN` branch.

Other stacks: Prisma `upsert` with a fixed `where`; Laravel seeders using `updateOrCreate` and `DB::transaction` in the signup action.

## Verify

- [ ] `[M]` Running `seed:reference` twice leaves identical row counts and no errors.
- [ ] `[M]` `seed:demo` against a production-like URL exits before writing.
- [ ] `[M]` Searching the demo data for real-looking phones, national ids or non-`example.com` emails finds none.
- [ ] `[S]` Forcing a failure after the tenant insert leaves zero tenants, users and defaults.
- [ ] `[S]` Two parallel signups with one slug create exactly one tenant with one set of defaults.
- [ ] `[A]` Upgrading defaults to a new version does not overwrite a tenant's edited role name.

## Pitfalls

- **`INSERT` without a conflict rule in a seed** → duplicates on rerun → fixed key and `ON CONFLICT`.
- **Random uuids for referenced rows** → ids differ per environment, code breaks → fixed ids or codes.
- **Defaults created after the signup response in a job** → user lands in an empty tenant → same transaction.
- **Demo data scraped from production** → real personal data in dev → generate fake data.
- **Seed script editing tenant-owned rows** → overwrites customer changes → only touch system rows.
