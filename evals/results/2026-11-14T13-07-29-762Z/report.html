## 📊 نسبة العملاء اللي رجعوا اشتروا تاني خلال 30 يوم

**الإجابة:** احسب نسبة العملاء اللي عملوا طلب تاني خلال 30 يوم من أول طلب ليهم، من بين كل العملاء اللي عدّى على أول طلب ليهم 30 يوم على الأقل. الـ query تحت بتطلعها.
**الثقة:** متوسطة. الرقم صح من ناحية الطريقة، لكن لازم تأكد من قيم `status` عندك ومن وجود `customer_id` في كل الطلبات.

(اقتراح سريع: شغّل `/sabry-kit:kit-setup` مرة واحدة، دقيقتين بس، عشان الردود تمشي على إعداداتك.)

### التعريف
- **البسط:** عملاء ليهم طلب تاني (صالح) تاريخه `<=` تاريخ أول طلب + 30 يوم.
- **المقام:** كل العملاء اللي أول طلب صالح ليهم عدّى عليه 30 يوم أو أكتر. من غير الشرط ده العملاء الجداد هيقلّلوا النسبة ظلم، لأن لسه معدّاش عليهم وقت يرجعوا.
- **الاستبعاد:** الطلبات الملغية والفاشلة والمرتجعة، والطلبات اللي `customer_id` فيها `NULL` (guest checkout).
- **التوقيت:** `created_at` زي ما هو متخزّن. لو عايز حدود اليوم بتوقيت القاهرة، حوّله بـ `AT TIME ZONE`.

### Query (PostgreSQL)
غيّر قيم `status` حسب اللي عندك:

```sql
WITH ranked AS (
  SELECT
    customer_id,
    created_at,
    ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at) AS rn
  FROM orders
  WHERE customer_id IS NOT NULL
    AND status NOT IN ('cancelled', 'failed', 'refunded')
),
first_order AS (
  SELECT customer_id, created_at AS first_at FROM ranked WHERE rn = 1
),
second_order AS (
  SELECT customer_id, created_at AS second_at FROM ranked WHERE rn = 2
)
SELECT
  COUNT(*) AS customers,
  COUNT(*) FILTER (WHERE s.second_at <= f.first_at + INTERVAL '30 days') AS repeaters,
  ROUND(
    100.0 * COUNT(*) FILTER (WHERE s.second_at <= f.first_at + INTERVAL '30 days') / COUNT(*),
    1
  ) AS repeat_rate_pct
FROM first_order f
LEFT JOIN second_order s USING (customer_id)
WHERE f.first_at <= now() - INTERVAL '30 days';
```

**نسخة cohort شهرية** لو عايز تشوف الاتجاه: ضيف `date_trunc('month', f.first_at) AS cohort_month` في الـ `SELECT`، وبعدها `GROUP BY 1 ORDER BY 1`. كده تعرف النسبة بتتحسن ولا بتسوء.

### ملاحظات على البيانات
- لو `status` عندك فيها قيم زي `pending` أو `paid`، حدّد أنهي حالات تتحسب "طلب فعلي". الأأمن غالبًا إنك تحسب `paid` / `completed` / `delivered` بس.
- **Guest checkout:** لو في طلبات من غير `customer_id`، العملاء دول مش هيتحسبوا، والنسبة هتطلع أقل من الحقيقة. قارن عدد الطلبات من غير `customer_id` بالإجمالي.
- **طلبين في نفس اليوم** (مثلًا نسي حاجة وطلبها بعدها بساعة) هيتعدّوا "رجوع". لو ده مش قصدك، اشترط `second_at >= first_at + INTERVAL '1 day'`.
- لو عدد العملاء في الـ cohort صغير (أقل من 100 تقريبًا)، اعتبر النسبة تقدير مش رقم نهائي.
- لو الجدول كبير، حط index على `(customer_id, created_at)`.

### توصيتي
شغّل الـ query الأول من غير تعديل وابعتلي النتيجة وقيم `status` الفعلية عندك. لو الرقم غريب، هنراجع تعريف "طلب صالح" قبل ما نبني عليه أي قرار. بعد كده اعمل النسخة الشهرية وتابعها كل شهر.

لو بتستخدم MySQL أو غيره، قولي وأحوّل لك الصيغة.

## التعريف

أنسب تعريف هو: **من بين العملاء اللي عملوا أول طلب، كام % منهم عملوا طلب تاني خلال 30 يوم من أول طلب.**

## الاستعلام (PostgreSQL)

```sql
WITH valid_orders AS (
    SELECT customer_id, created_at
    FROM orders
    WHERE status NOT IN ('cancelled', 'failed', 'refunded')  -- عدّلها حسب قيم status عندك
),
first_orders AS (
    SELECT customer_id, MIN(created_at) AS first_order_at
    FROM valid_orders
    GROUP BY customer_id
),
repeaters AS (
    SELECT DISTINCT f.customer_id
    FROM first_orders f
    JOIN valid_orders o
      ON o.customer_id = f.customer_id
     AND o.created_at >  f.first_order_at
     AND o.created_at <= f.first_order_at + INTERVAL '30 days'
)
SELECT
    COUNT(DISTINCT f.customer_id)                                   AS total_customers,
    COUNT(DISTINCT r.customer_id)                                   AS repeat_customers,
    ROUND(100.0 * COUNT(DISTINCT r.customer_id)
          / NULLIF(COUNT(DISTINCT f.customer_id), 0), 2)            AS repeat_rate_pct
FROM first_orders f
LEFT JOIN repeaters r USING (customer_id)
WHERE f.first_order_at <= NOW() - INTERVAL '30 days';  -- بس العملاء اللي عدّت عليهم 30 يوم
```

## نقاط مهمة

1. **فلتر الـ `status`:** استبعد الطلبات الملغية أو الفاشلة أو المرتجعة، وإلا هتتحسب شراء وهو مش حقيقي. غيّر القيم حسب اللي عندك.
2. **شرط `first_order_at <= NOW() - 30 days`:** العميل اللي أول طلب له من 5 أيام لسه معداش عليه 30 يوم. لو حسبته هيقلل النسبة بشكل غلط.
3. **`created_at > first_order_at`:** عشان أول طلب ميتحسبش هو نفسه "طلب تاني". لو العميل عمل طلبين في نفس اللحظة بالظبط، هيتحسب الاتنين كأنهم طلب واحد. لو ده ممكن عندك، استخدم `ROW_NUMBER()` بدل المقارنة بالوقت.
4. **عملاء الـ guest:** لو في طلبات `customer_id` فيها `NULL`، استبعدها بـ `AND customer_id IS NOT NULL`.

## نسخة شهرية (cohort)

لو عايز تشوف النسبة لكل شهر عشان تتابع هل بتتحسن:

```sql
-- نفس الـ CTEs فوق، وبعدين:
SELECT
    DATE_TRUNC('month', f.first_order_at)::date AS cohort_month,
    COUNT(*)                                    AS new_customers,
    COUNT(r.customer_id)                        AS repeaters,
    ROUND(100.0 * COUNT(r.customer_id) / COUNT(*), 2) AS repeat_rate_pct
FROM first_orders f
LEFT JOIN repeaters r USING (customer_id)
WHERE f.first_order_at <= NOW() - INTERVAL '30 days'
GROUP BY 1
ORDER BY 1;
```

## 🔌 Integration: بوابة دفع (Hono + Drizzle)
**المصدر:** الإجابة هنا قاعدة عامة، مش من docs بوابة معيّنة. لما تحدد البوابة (Paymob / Stripe / Fawry / Tap) أقرأ docs بتاعتها قبل أي تنفيذ.

### الإجابة المباشرة
**علّم الطلب "مدفوع" من الـ webhook بس، ومن صفحة الرجوع (redirect) أبداً.**

- صفحة الرجوع بيفتحها المتصفح، والعميل يقدر يعدّل الرابط أو يقفل التاب قبل ما توصل.
- الـ webhook هو اللي بيجيلك من سيرفر البوابة لسيرفرك مباشرة، وهو المصدر الموثوق.

### Flow
1. العميل يضغط "ادفع". السيرفر ينشئ الطلب بحالة `pending` ويبعت للبوابة طلب إنشاء دفعة (فيه idempotency key ومرجع طلبك).
2. السيرفر يحوّل العميل لصفحة البوابة، وهي بترجّعه لموقعك بعد الدفع.
3. **صفحة الرجوع:** تعرض "جاري تأكيد الدفع…" وتقرأ حالة الطلب من الـ DB. ممنوع تغيّر الحالة فيها.
4. **الـ webhook:** يوصل على endpoint في Hono، ومنه تتحول الحالة إلى `paid`.
5. صفحة الرجوع تعمل polling خفيف (كل 2–3 ثواني لمدة محدودة) على حالة الطلب. لو الـ webhook اتأخر، تظهر رسالة "هنأكد لك بالإيميل".

### Webhook handler (بالترتيب)
1. اقرأ الـ **raw body** (في Hono `c.req.text()` قبل أي parse) وتحقق من التوقيع (HMAC).
2. سجّل `event_id` في جدول أحداث بـ unique constraint. لو موجود يبقى تكرار، فرجّع 2xx وبس.
3. **ما تثقش في الـ payload لوحده:** اجلب الدفعة من API البوابة وتأكد من الحالة والمبلغ والعملة ومرجع الطلب.
4. حدّث الطلب بـ transaction واحدة وبشرط `WHERE status = 'pending'`. ده بيخلي التنفيذ مرتين آمن، ويمنع الرجوع من `paid` لحالة أقدم لو الأحداث وصلت بالعكس.
5. رجّع 2xx بسرعة. الشغل التقيل (إيميل، فاتورة، شحن) يتعمل في queue بعد كده.

### Failure handling
| الفشل | العميل يشوف | النظام يعمل |
|---|---|---|
| الـ webhook اتأخر | "جاري التأكيد" | polling ثم job مطابقة |
| الـ webhook اتكرر | لا شيء | يتجاهله بفضل `event_id` |
| المبلغ لا يطابق الطلب | "الدفع قيد المراجعة" | يعلّم الطلب `review` ويرسل alert |
| التوقيع غلط | لا شيء | 401 وتسجيل المحاولة |
| فشل الدفع / إلغاء | "الدفع لم يتم" | `failed` مع إمكانية إعادة المحاولة |

### Data (Drizzle)
- المبلغ **integer بالوحدة الصغرى** (قرش/سنت) مع عمود currency، ومش float.
- أعمدة الطلب: `status` (`pending → paid | failed | expired`، وانتقالات مسموحة فقط)، `provider_payment_id`، `paid_at`.
- جدول `payment_events` فيه `event_id` unique ونتيجة المعالجة.

### Security
- مفاتيح البوابة وسر الـ webhook في env فقط.
- أي تعامل مع بيانات الكارت بيحصل في صفحة البوابة. ما تلمسش بيانات كارت في سيرفرك.

### Go-live
- عنوان الـ webhook مسجّل في لوحة البوابة (live مش sandbox).
- job مطابقة مجدول (كل ساعة مثلاً) يقارن الطلبات `pending` القديمة بحالتها عند البوابة، لأن حدثاً ما هيضيع في وقت ما.
- Alert على فشل التحقق من التوقيع وعلى حالة `review`.
- تجربة دفع حقيقية واحدة بمبلغ صغير من الأول للآخر قبل الإطلاق.

## ليه مش من صفحة الرجوع؟
- الـ redirect بييجي من المتصفح، فأي حد يقدر يفتح `/payment/success?order=123` بإيده.
- العميل ممكن يقفل التاب قبل ما يرجع، فتفضل الفلوس مدفوعة والطلب "pending".
- الـ webhook بييجي من الجيت واي لسيرفرك مباشرة، وبيتوقّع بتوقيع تقدر تتحقق منه.

## الفلو الصح
1. **إنشاء الطلب:** تعمل الطلب بحالة `pending`، وتحفظ `paymentReference` أو `intentId` اللي رجع من الجيت واي.
2. **الـ webhook:** الجيت واي يبعت لـ `/webhooks/payment`، وإنت تعمل التالي:
   - تتحقق من التوقيع (HMAC أو signature header) على الـ **raw body**.
   - تدوّر على الطلب بالـ reference.
   - تتأكد إن المبلغ والعملة مطابقين للطلب.
   - تعمل update **idempotent**.
   - ترجّع `200` بسرعة.
3. **صفحة الرجوع:** تعرض الحالة بس. تقرأ حالة الطلب من الـ DB، وتعمل polling بسيط لو لسه `pending`. ولو حبيت، تسأل الـ API بتاع الجيت واي مباشرة عن حالة الدفع كتأكيد إضافي.

## مثال (Hono + Drizzle)

```ts
app.post('/webhooks/payment', async (c) => {
  const raw = await c.req.text(); // raw body مش json()
  const sig = c.req.header('x-signature') ?? '';

  if (!verifySignature(raw, sig, process.env.PAYMENT_WEBHOOK_SECRET!)) {
    return c.text('invalid signature', 401);
  }

  const event = JSON.parse(raw);
  if (event.status !== 'paid') return c.text('ignored', 200);

  await db.transaction(async (tx) => {
    const [order] = await tx.select().from(orders)
      .where(eq(orders.paymentRef, event.reference))
      .for('update'); // قفل الصف (Postgres)

    if (!order) return;
    if (order.status === 'paid') return; // idempotent: الـ webhook ممكن يتبعت مرتين
    if (order.totalCents !== event.amountCents || order.currency !== event.currency) {
      // مبلغ مش مطابق: سجّله للمراجعة وماتعلّمش مدفوع
      return;
    }

    await tx.update(orders)
      .set({ status: 'paid', paidAt: new Date() })
      .where(eq(orders.id, order.id));
  });

  return c.text('ok', 200);
});
```

التوقيع بيتحقق بـ `crypto.createHmac('sha256', secret)` وبعدين `timingSafeEqual`. بس الصيغة بتختلف من جيت واي للتاني.

## نقاط مهمة
- **Idempotency:** الجيت واي بيعيد إرسال الـ webhook لو ماردّيتش بـ 200. فالشرط `status === 'paid'` ضروري. وممكن كمان تعمل جدول `webhook_events` بـ unique على الـ event id.
- **المبلغ:** قارنه دايمًا بالـ DB. ماتثقش في مبلغ جاي من العميل.
- **الحالات التانية:** استقبل `failed` و`refunded` و`expired` كمان، مش `paid` بس.
- **الأسرار:** خلّي الـ webhook secret في env، وماتلوجش الـ payload كامل لو فيه بيانات كارت أو عميل.
- **التجربة:** استخدم sandbox بتاع الجيت واي، وجرّب تبعت نفس الـ webhook مرتين، وجرّب توقيع غلط.

قولّي الجيت واي اللي هتستخدمه (Paymob، Fawry، Stripe، Kashier...) وأنا أكتبلك التحقق من التوقيع بالظبط. ولو عايز، أبص على الـ schema بتاع `orders` في المشروع وأعدّل عليه.

## 📱 Mobile — طلبات بتضيع لما النت يقطع

**التوصية:** اعمل **Outbox Queue** محلية (طابور كتابة دائم) مع **Idempotency Key** لكل طلب. الطلب ماينفعش يتبعت مباشرة من الشاشة. الشاشة تكتبه في الطابور المحلي الأول، وعامل خلفي هو اللي يبعته.

### التصميم

1. **تحفظ الأول وتبعت بعدين.** أي عملية كتابة (POST/PUT/DELETE) تتسجل في تخزين محلي دائم قبل أي محاولة إرسال. الحقول: `id` (UUID)، `endpoint`، `payload`، `createdAt`، `attempts`، `status`.
2. **Idempotency Key.** الـ UUID يتولّد عند المستخدم وقت إنشاء الطلب، ويتبعت كـ header. من غيره، لو الرد ضاع بعد ما السيرفر نفّذ، الـ retry هيعمل عملية مكررة (دفع مرتين أو أوردر مكرر). ده الخطر الأكبر في التصميم.
3. **الإرسال والـ retry.**
   - الـ worker يشتغل عند فتح التطبيق، وعند رجوع النت (`@react-native-community/netinfo`)، وبـ timer.
   - الـ backoff أُسّي مع jitter.
   - أخطاء الشبكة و5xx و429 تتعمل لها retry.
   - أخطاء 4xx (غير 408/429) تتعلّم `failed` ومتتعملش لها retry، والمستخدم يشوف السبب.
   - الإرسال بالترتيب لو العمليات معتمدة على بعض.
4. **التخزين.** استخدم MMKV أو SQLite (مثلاً WatermelonDB أو `expo-sqlite`)، **مش** AsyncStorage للطابور الكبير. الـ Tokens وأي secrets في secure storage، ومتتخزنش جوه الطابور بشكل مكشوف.
5. **UX (الحالات الأربع).**
   - Optimistic UI: العنصر يظهر فوراً بحالة "في الانتظار".
   - Loading: أيقونة ساعة أو "جارٍ الإرسال".
   - Error: "فشل الإرسال" مع زرار إعادة المحاولة أو حذف.
   - Success: تتشال العلامة بعد تأكيد السيرفر.
   - لو الإرسال فشل نهائياً، رجّع الحالة (rollback) وقول للمستخدم.
6. **الـ app killed.** الطابور دائم، فأي عملية لسه `pending` أو `sending` تتعاد عند الفتح. حالة `sending` لازم تتحوّل لـ `pending` عند بداية التشغيل، والـ Idempotency Key هو اللي يمنع التكرار.

- يخزّن الـ Idempotency Key مع نتيجة العملية لمدة (24–72 ساعة) ويرجّع نفس الرد لو اتبعت تاني.
- الـ API يكون متوافق مع النسخ القديمة من التطبيق اللي لسه متسطّبة.

# تصميم حل لضياع الطلبات وقت انقطاع النت

الفكرة الأساسية: **متبعتش الطلب مباشرة من الشاشة**. احفظه الأول في طابور محلي دائم (persistent queue)، وخلّي عامل (worker) منفصل يبعته لما النت يرجع.

## المكونات

1. **كشف حالة الشبكة**: استخدم `@react-native-community/netinfo`. اعتمد على `isInternetReachable` مش `isConnected` بس، لأن الاتصال بالواي فاي ممكن يبقى من غير نت فعلي.
2. **طابور دائم**: خزّن الطلبات في MMKV أو SQLite (مثل WatermelonDB أو op-sqlite). ما تستخدمش state في الذاكرة، لأنه بيضيع لو التطبيق اتقفل.
3. **Worker**: بيسحب الطلبات من الطابور بالترتيب ويبعتها، ويحذف الطلب بعد نجاحه فقط.
4. **Retry مع exponential backoff + jitter**: مثلاً 1s ثم 2s ثم 4s ... بحد أقصى. أعد المحاولة في أخطاء الشبكة و5xx فقط. أخطاء 4xx تعتبر فشل نهائي ولازم تتعامل معاها.
5. **Idempotency key**: ولّد UUID لكل طلب وقت إنشائه، وابعته في header مثل `Idempotency-Key`. السيرفر يتجاهل التكرار. ده مهم جدًا، لأن الطلب ممكن يوصل السيرفر والرد هو اللي يضيع، فتعيد الإرسال وتتكرر العملية (دفع مرتين مثلًا).
6. **Optimistic UI**: اعرض للمستخدم إن العملية "قيد الإرسال" بدل ما تفشل قدامه، وحدّث الحالة لما تنجح أو تفشل.

## كود مبسّط

```ts
import NetInfo from '@react-native-community/netinfo';
import { MMKV } from 'react-native-mmkv';
import uuid from 'react-native-uuid';

const storage = new MMKV();
const KEY = 'outbox';

type Job = { id: string; url: string; method: string; body: any; attempts: number };

const load = (): Job[] => JSON.parse(storage.getString(KEY) ?? '[]');
const save = (q: Job[]) => storage.set(KEY, JSON.stringify(q));

export function enqueue(url: string, method: string, body: any) {
  const q = load();
  q.push({ id: uuid.v4() as string, url, method, body, attempts: 0 });
  save(q);
  flush();
}

let flushing = false;
export async function flush() {
  if (flushing) return;
  flushing = true;
  try {
    let q = load();
    while (q.length) {
      const job = q[0];
      try {
        const res = await fetch(job.url, {
          method: job.method,
          headers: { 'Content-Type': 'application/json', 'Idempotency-Key': job.id },
          body: JSON.stringify(job.body),
        });
        if (res.ok || (res.status >= 400 && res.status < 500)) {
          q.shift();                 // نجح، أو فشل نهائي (يُسجَّل/يُبلَّغ عنه)
          save(q);
        } else throw new Error('server');
      } catch {
        job.attempts++;
        save(q);
        await new Promise(r => setTimeout(r, Math.min(30000, 2 ** job.attempts * 1000) * (0.5 + Math.random())));
        q = load();
        if (!navigator.onLine && job.attempts > 5) break;
      }
    }
  } finally { flushing = false; }
}

// شغّل الـ flush لما النت يرجع أو التطبيق يفتح
NetInfo.addEventListener(s => { if (s.isInternetReachable) flush(); });
```

## 2. التصميم

**جداول جديدة:**
- `coupons`:
  - الكود: unique وبيتخزن normalized (uppercase وtrim).
  - النوع: `percent` أو `fixed`.
  - القيمة، وتاريخ البداية والانتهاء.
  - `max_uses` و`used_count` و`max_uses_per_user`.
  - `min_order_amount` و`is_active`.
- `coupon_redemptions`:
  - `coupon_id` و`order_id` و`user_id` و`discount_amount` و`created_at`.
  - فيه unique على `(coupon_id, order_id)`.
- جدول `orders` يتزود فيه `coupon_id` و`discount_amount`.

**API بتاع الأدمن (Hono):** إنشاء كوبون، وتعديله، وتفعيله أو تعطيله، وعرض القايمة مع `used_count`. كل ده محمي بـ middleware للأدمن، وفيه validation بـ Zod:

- المبلغ الثابت أكبر من صفر.
- تاريخ الانتهاء في المستقبل.

**API بتاع العميل:**
- `POST /coupons/validate`: معاينة بس، ومبتحجزش حاجة. بترجّع الخصم المحسوب أو سبب الرفض.
- الكوبون بيتطبق فعليًا جوه `POST /orders` (الـ checkout) فقط.

**قاعدة ذهبية:** السيرفر هو اللي بيحسب الخصم والإجمالي. الفرونت مبيبعتش أي مبلغ، بيبعت الكود بس.

## 3. التزامن (الجزء الحساس)

الخطر هو طلبين في نفس اللحظة يقراوا `used_count = 9` من 10 ويعدّوا الاتنين. الحل:

1. كل خطوات الطلب تتعمل في **transaction واحدة**: إنشاء الطلب، وحجز الكوبون، وتسجيل الاستخدام.
2. الحجز بـ **UPDATE شرطي ذري** على صف الكوبون، بشروط `used_count < max_uses` والكوبون فعّال وغير منتهي. لو الصفوف المتأثرة صفر، الكوبون مرفوض. مفيش read-then-write في طبقة التطبيق خالص.
3. الحد لكل عميل بيتفرض بالطريقة نفسها: إما unique constraint، وإما lock على صف الكوبون جوه الـ transaction. الـ count المجرد من غير lock مش كفاية.
4. الـ unique على `(coupon_id, order_id)` يمنع تسجيل نفس الاستخدام مرتين لو الريكوست اتعاد (retry).
5. التحقق من تاريخ الانتهاء بيتعمل وقت الحجز جوه الـ transaction، مش وقت الـ validate بس.
6. **الإرجاع:** لو الطلب اتلغى أو الدفع فشل، التاكس ينقص `used_count` ويمسح صف الـ redemption في transaction. ممكن تلغي الطلب التلقائي لو الدفع ما تمش في مدة معينة.
7. **تأكيد الدفع:** لو بوابة الدفع خارجية، نقرر هل الحجز يتم عند إنشاء الطلب (pending مع مهلة) ولا عند تأكيد الدفع. المقترح هو الحجز عند الإنشاء مع مهلة انتهاء.

## 🔍 SEO: صفحات المنتجات مش بتظهر

### 1. الأول: هل الصفحات مفهرسة أصلاً؟ (10 دقايق)
- في Google Search Console اعمل URL Inspection لـ 3 صفحات منتجات (واحدة عربي وواحدة إنجليزي).
- افتح تقرير Pages وشوف السبب في "Not indexed". الأسباب المعتادة:
  - `Discovered, currently not indexed` معناها إن جوجل لقاها ومجاش يزحف عليها (crawl budget أو جودة ضعيفة).
  - `Crawled, currently not indexed` معناها إن جوجل شافها ورفضها (محتوى رفيع أو مكرر).
  - `Duplicate, Google chose different canonical` معناها مشكلة canonical.
  - `Excluded by noindex` أو `Blocked by robots.txt` معناها حظر صريح.
- لو الموقع مش متسجّل في Search Console، ده أول حاجة تعملها.
- اكتب في جوجل `site:yourdomain.com/products` عشان تعرف عدد الصفحات المفهرسة تقريباً.

### 2. الحظر التقني (الأسباب الأشهر في Next.js)
| الفحص | إزاي |
|---|---|
| `noindex` متروك من staging | ابحث عن `robots` في `metadata` وفي الـ headers وفي `X-Robots-Tag` |
| `robots.txt` بيمنع `/products` أو `/_next/` | افتح `/robots.txt` على الموقع الحي |
| الصفحة بتترندر فاضية بدون JS | `curl -s URL` وشوف هل اسم المنتج وتفاصيله موجودة في الـ HTML. لو لأ، المنتجات بتتحمّل client-side بـ `useEffect` |
| مفيش sitemap، أو الـ sitemap مش فيه المنتجات | افتح `/sitemap.xml` وتأكد إن فيه روابط المنتجات بالعربي والإنجليزي |
| مفيش روابط داخلية `<a href>` للمنتجات | لو التنقل بـ `onClick` أو router.push، جوجل مش هيلاقيها |
| `canonical` غلط (كله بيشاور على الـ home أو على نسخة واحدة) | افحص `<link rel="canonical">` في كل لغة |
| `hreflang` ناقص أو من غير تبادل | كل نسخة لازم تشاور على الثانية وعلى نفسها |
| `notFound()` أو redirect loop على الـ dynamic routes | جرّب الروابط الفعلية بـ `curl -I` |

### 3. حاجات خاصة بالموقع ثنائي اللغة
- كل لغة ليها URL مستقل (`/ar/...` و`/en/...`)، مش نفس الـ URL بيتغيّر بالكوكي أو الـ Accept-Language.
- `<html lang="ar" dir="rtl">` على النسخة العربية.
- `alternates.languages` في `generateMetadata`، مع `x-default`.
- الـ `title` والـ `description` مكتوبين بالعربي للنسخة العربية. مش ترجمة آلية ولا نفس النص الإنجليزي.

### 4. بعد ما الفهرسة تتحل
- **Structured data:** `Product` schema (الاسم والصورة والسعر والتوفر) لازم يطابق اللي ظاهر في الصفحة. من غير تقييمات مخترعة.
- **المحتوى:** وصف فريد لكل منتج. الوصف المنسوخ من المورّد هو سبب شائع لـ "Crawled, not indexed".
- **Core Web Vitals:** افحص الـ template (LCP للصور، CLS)، مش صفحة واحدة بس.

1. Search Console وفحص أسباب عدم الفهرسة. تأثيره أعلى حاجة وجهده قليل.

## 1. اتأكد من حالة الصفحات في Google Search Console

  - **"Discovered – currently not indexed"**: جوجل عارف الصفحة بس مش شايف إنها تستاهل الزحف. السبب غالبًا ضعف internal links أو محتوى مكرر أو رفيع.

## 2. أكتر أسباب شيوعًا في Next.js
1. **الـ rendering**: لو صفحات المنتجات بتجيب الداتا في `useEffect` أو client component، الـ HTML الأولي بيطلع فاضي. استخدم Server Components أو SSG/ISR. اعمل `curl -s https://yourdomain.com/ar/products/xyz` وتأكد إن اسم المنتج وسعره موجودين في الـ HTML.

3. **`robots.txt`**: افتح `/robots.txt` وتأكد إنه مش عامل `Disallow` على `/products` أو `/ar`.
4. **`sitemap.xml`**: لازم يكون موجود ومتقدّم في Search Console. وتأكد إنه فيه روابط المنتجات بكل اللغات.
5. **الـ canonical**: كل صفحة لازم تشاور على نفسها. لو كل المنتجات canonical بتاعها الصفحة الرئيسية، جوجل هيتجاهلها.
6. **الروابط الداخلية**: لو المنتجات متاحة بس عن طريق search أو JS pagination (`onClick` من غير `<a href>`)، جوجل مش هيلاقيها. استخدم `<Link>` عادي.

## 3. إعدادات اللغتين (hreflang)
- كل لغة ليها URL مستقل (`/ar/...` و`/en/...`)، مش cookie أو تغيير بالـ JS.
- حط `alternates.languages` في `generateMetadata` عشان يطلع `hreflang` متبادل بين النسختين، مع `x-default`.
- لو middleware الـ i18n بيعمل redirect حسب `Accept-Language` أو الـ IP، جوجل (بيزحف من US) هيشوف نسخة واحدة بس. اسمح بالوصول المباشر لكل URL من غير redirect.
- حط `lang` و`dir="rtl"` على `<html>` للعربي.

## 4. بعد كده
- الـ status code لازم يكون 200 (مش 307/308 متسلسلة، ومش soft-404).
- حط structured data من نوع `Product` (JSON-LD).
- محتوى فريد لكل منتج: لو الوصف مكرر أو مترجم آليًا بالكامل، جوجل بيرفضه كتير.
- اطلب indexing لعيّنة صغيرة من الصفحات بعد التصليح، وبعدها راقب تقرير **Pages**.
