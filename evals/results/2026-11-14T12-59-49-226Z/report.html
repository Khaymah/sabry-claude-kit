## أبدأ إزاي: RAG

ابدأ بـ **RAG** (Retrieval-Augmented Generation). مش fine-tuning. الموديل بيجيب المقاطع المناسبة من مستنداتك وقت السؤال ويجاوب منها. مستنداتك بتتغير، وده بيسمح لك تحدّثها من غير ما تدرّب الموديل تاني. وكمان تقدر تعرض المصدر للعميل.

1. **جهّز المستندات:** حوّلها لنص نضيف (PDF وصفحات الموقع وFAQ). قسّمها chunks حوالي 300–800 token، واحتفظ بالعنوان والمصدر مع كل chunk. جودة المستندات بتأثر في النتيجة أكتر من اختيار الموديل.
2. **الفهرسة:** embeddings في قاعدة vector. لو عندك PostgreSQL، `pgvector` كفاية في البداية ومحتاجش خدمة منفصلة.
3. **الاسترجاع:** hybrid search (keyword + vector). ده أحسن مع أسماء المنتجات وأرقام الموديلات.
4. **التوليد:** الـ system prompt يقول للموديل:
   - جاوب من المقاطع المسترجعة بس.
   - لو الإجابة مش موجودة، قول "معنديش معلومة مؤكدة" وحوّل لموظف.
   - اذكر المصدر.
5. **التحويل لبشري:** زرار واضح، وتلقائي لو الثقة قليلة أو العميل زعلان.
6. **الأمان:** النص المسترجع والرسائل بيتعاملوا كبيانات مش أوامر (prompt injection). متديش الموديل صلاحية تنفيذ حاجة (استرجاع فلوس مثلًا) من غير تأكيد سيرفر. ولو في بيانات عملاء، افصل الصلاحيات.
7. **Evals قبل الإطلاق:** اعمل 50–100 سؤال حقيقي من تذاكر الدعم القديمة مع الإجابة الصح. قس عليهم قبل الإطلاق وبعد أي تغيير.

## الفكرة: RAG
الموديل مش بيحفظ مستندات الشركة. بتدوّر عن الأجزاء المناسبة وقت السؤال وتبعتها له مع السؤال:

1. **تجهيز المستندات:** حوّل PDF/Word/صفحات المساعدة لنص، وقسّمه أجزاء (chunks) حوالي 300–800 كلمة، مع الحفاظ على العناوين.
2. **الفهرسة:** اعمل embeddings لكل جزء وخزنها في vector DB. لو عدد المستندات صغير، pgvector على PostgreSQL كفاية. تقدر كمان تضيف بحث بالكلمات المفتاحية (hybrid)، لأنه بيفيد في أسماء المنتجات وأرقام الطلبات.
3. **وقت السؤال:** هات أفضل 5–10 أجزاء، وابعتها للموديل مع تعليمات صارمة: "جاوب من المستندات فقط، ولو الإجابة مش موجودة قول إنك مش عارف وحوّل لموظف".
4. **عرض الإجابة:** اعرض مصدر كل إجابة. ده بيبني الثقة وبيسهّل اكتشاف الأخطاء.
5. **التسليم لموظف:** لازم يبقى فيه زرار "كلم موظف"، وتحويل تلقائي لما الثقة تقل أو العميل يتضايق.

لو المستندات قليلة (مثلاً أقل من حوالي 100 صفحة)، ممكن تحطها كلها في الـ prompt مع prompt caching من غير vector DB. ده أبسط بكتير كبداية.

## التعريف

الأشهر هو **30-day repeat rate** على مستوى الـ cohort:

> من العملاء اللي عملوا **أول طلب** ليهم، كام % منهم عملوا **طلب تاني خلال 30 يوم** من أول طلب؟

## الاستعلام (PostgreSQL)

```sql
WITH valid_orders AS (
  SELECT customer_id, created_at
  FROM orders
  WHERE status NOT IN ('cancelled', 'failed', 'refunded')
),
first_orders AS (
  SELECT customer_id, MIN(created_at) AS first_at
  FROM valid_orders
  GROUP BY customer_id
)
SELECT
  COUNT(*) AS customers,
  COUNT(*) FILTER (
    WHERE EXISTS (
      SELECT 1
      FROM valid_orders v
      WHERE v.customer_id = f.customer_id
        AND v.created_at > f.first_at
        AND v.created_at <= f.first_at + INTERVAL '30 days'
    )
  ) AS repeaters,
  ROUND(
    100.0 * COUNT(*) FILTER (
      WHERE EXISTS (
        SELECT 1
        FROM valid_orders v
        WHERE v.customer_id = f.customer_id
          AND v.created_at > f.first_at
          AND v.created_at <= f.first_at + INTERVAL '30 days'
      )
    ) / NULLIF(COUNT(*), 0),
    1
  ) AS repeat_rate_pct
FROM first_orders f
WHERE f.first_at <= now() - INTERVAL '30 days';
```

## نقاط لازم تنتبه لها

1. **الـ status:** أنا استبعدت `cancelled / failed / refunded`. عدّل القائمة حسب القيم الفعلية عندك، وشوفها الأول بـ `SELECT DISTINCT status FROM orders`.
2. **شرط `first_at <= now() - 30 days`:** من غيره العملاء الجداد هيقلّلوا النسبة ظلم، لأن الـ 30 يوم بتاعتهم لسه ما خلصتش.
3. **الضيوف (guest checkout):** لو `customer_id` فاضي لبعض الطلبات، العميل ده مش هيتحسب. اتأكد إن الـ id ثابت لنفس الشخص، أو استخدم الإيميل أو التليفون كبديل.
4. **طلبات في نفس اللحظة:** لو العميل بيقسّم سلة واحدة على أكتر من order، ممكن تتحسب تكرار غلط. وقتها خلّي الشرط `created_at > first_at + INTERVAL '1 day'` أو جمّع الطلبات حسب اليوم.

## لو عايز تطوّره

- **حسب الشهر:** اعمل `GROUP BY date_trunc('month', first_at)` عشان تشوف الاتجاه، هل النسبة بتتحسن ولا لأ.
- **المقياس البديل:** لو منتجاتك استهلاكية، جرّب 60 أو 90 يوم. الـ 30 يوم ممكن تكون قصيرة على المنتجات اللي بتخلص ببطء.

# نسبة العملاء اللي رجعوا اشتروا خلال 30 يوم

التعريف اللي هستخدمه: العميل "رجع" لو عنده طلب تاني خلال 30 يوم من **أول طلب** له.

## الاستعلام (PostgreSQL)

```sql
WITH valid_orders AS (
    SELECT customer_id, created_at
    FROM orders
    WHERE status NOT IN ('cancelled', 'failed', 'refunded')  -- عدّلها حسب قيم الـ status عندك
),
first_orders AS (
    SELECT customer_id, MIN(created_at) AS first_order_at
    FROM valid_orders
    GROUP BY customer_id
),
repeaters AS (
    SELECT DISTINCT f.customer_id
    FROM first_orders f
    JOIN valid_orders o
      ON o.customer_id = f.customer_id
     AND o.created_at >  f.first_order_at
     AND o.created_at <= f.first_order_at + INTERVAL '30 days'
)
SELECT
    COUNT(*)                                        AS total_customers,
    COUNT(r.customer_id)                            AS repeat_customers,
    ROUND(100.0 * COUNT(r.customer_id) / COUNT(*), 2) AS repeat_rate_pct
FROM first_orders f
LEFT JOIN repeaters r USING (customer_id)
WHERE f.first_order_at <= NOW() - INTERVAL '30 days';  -- عشان العملاء الجداد ما يقلّلوش النسبة
```

## نقاط مهمة

1. **فلتر الـ status:** استبعد الطلبات الملغية أو الفاشلة، وإلا هتحسب عميل "رجع" وهو في الحقيقة لغى الطلب. شوف القيم الفعلية عندك بـ `SELECT DISTINCT status FROM orders`.
2. **شرط آخر سطر مهم:** العميل اللي أول طلب له من 10 أيام لسه معندوش فرصة كاملة 30 يوم. لو دخّلته في الحساب، النسبة هتطلع أقل من الحقيقة.
3. **`o.created_at > f.first_order_at`:** بيمنع إن أول طلب نفسه يتحسب كأنه عودة. لو العميل عمل طلبين في نفس اللحظة بالضبط، الطلب التاني مش هيتحسب. ده نادر، بس لو طلبك يحتمل تقسيم الطلب لسجلين، استخدم `ROW_NUMBER()` بدل المقارنة بالوقت.
4. **لو عندك guest checkout:** `customer_id` لو NULL لازم تستبعده بـ `AND customer_id IS NOT NULL`.

لو عايز تشوف النسبة لكل شهر عشان تتابع التحسن:

```sql
SELECT
    DATE_TRUNC('month', f.first_order_at) AS cohort_month,
    COUNT(*)                              AS customers,
    COUNT(r.customer_id)                  AS repeaters,

LEFT JOIN repeaters r USING (customer_id)
WHERE f.first_order_at <= NOW() - INTERVAL '30 days'
```

## التوصية: Outbox Queue + Idempotency Key

الفكرة إن الطلب ما يتبعتش مباشرة. بيتكتب الأول في طابور محلي دائم، وبعدين عامل منفصل يبعته ويعيد المحاولة لحد ما ينجح.

### الأجزاء (على الموبايل)

1. **تخزين دائم للطابور.** استخدم MMKV (سريع وبسيط) أو SQLite لو الطلبات كبيرة أو كتير. الطابور لازم يعيش بعد إغلاق التطبيق أو الكراش. أي طابور في الذاكرة بس يضيع مع الكراش.
2. **Idempotency key لكل عملية.** ولّد UUID وقت إنشاء العملية، مش وقت الإرسال، واحفظه مع الطلب. ده أهم جزء، وسببه إن الـ timeout غامض. ساعات الطلب يوصل للسيرفر والرد هو اللي يضيع، فلو أعدت الإرسال من غير key هتعمل طلب مكرر (أوردر مرتين مثلًا).
3. **حالات واضحة لكل عنصر:** `pending` ← `sending` ← `sent` أو `failed`. اعرضها في الـ UI (أيقونة ساعة، "فشل، اضغط للإعادة")، وعدّل الـ UI بشكل optimistic.
4. **متى تفرّغ الطابور (flush):** عند رجوع النت (`@react-native-community/netinfo`)، وعند رجوع التطبيق للـ foreground، وعند فتح التطبيق.
5. **سياسة إعادة المحاولة:**
   - **أعد المحاولة:** عند network error أو timeout أو 5xx أو 408 أو 429. استخدم exponential backoff مع jitter، واحترم `Retry-After`.
   - **لا تعيد:** عند 4xx الأخرى (400 أو 403 أو 422). ده خطأ في الطلب نفسه، فحوّله لـ `failed` واعرضه للمستخدم.
6. **الترتيب:** لو العمليات معتمدة على بعض (إنشاء ثم تعديل لنفس الكيان)، ابعتها بالتسلسل لكل كيان. المستقل منها ممكن يتبعت بالتوازي.
7. **الـ token:** جدّد الـ auth token قبل إعادة الإرسال. الطابور ممكن يفضل ساعات والـ token ينتهي.

### على السيرفر (مطلوب، من غيره الحل ناقص)

- ادعم header `Idempotency-Key`. خزّن المفتاح مع النتيجة (24 إلى 72 ساعة)، ولو جه نفس المفتاح تاني رجّع نفس الرد من غير ما تنفّذ مرة ثانية.
- اعمل unique constraint على المفتاح في الداتابيز، عشان طلبين متزامنين بنفس المفتاح ما ينفذوش الاتنين.

# الحل: طابور طلبات offline (Outbox Pattern)

الفكرة إنك متحاولش تبعت الطلب مباشرة. احفظه الأول محليًا، وبعدين ابعته لما النت يرجع.

## المكونات الأساسية

**1. كشف حالة الشبكة**
استخدم `@react-native-community/netinfo`:
```ts
import NetInfo from '@react-native-community/netinfo';

NetInfo.addEventListener(state => {
  if (state.isConnected && state.isInternetReachable) flushQueue();
});
```
شيّك على `isInternetReachable` مش `isConnected` بس. الجهاز ممكن يكون على WiFi من غير إنترنت فعلي.

**2. تخزين الطابور بشكل دائم**
لازم الطابور يفضل موجود حتى لو التطبيق اتقفل. استخدم:
- `MMKV`: سريع وبسيط، وهو الأنسب لمعظم الحالات.
- `SQLite` أو `WatermelonDB`: لو الطلبات كتير أو محتاج استعلامات.
- `AsyncStorage`: ينفع لكنه أبطأ.

كل عنصر في الطابور:
```ts
{
  id: uuid(),              // idempotency key
  method: 'POST',
  url: '/orders',
  body: {...},
  createdAt: Date.now(),
  retries: 0,
  status: 'pending'
}
```

**3. معالج الطابور (Flush)**
- ابعت الطلبات **بالترتيب** (FIFO) لو في اعتماد بينها.
- لو نجح الطلب، شيله من الطابور.
- لو فشل بسبب الشبكة، سيبه وجرّب تاني.
- لو فشل بخطأ 4xx (طلب غلط)، شيله أو علّمه `failed` ومترجّعش تحاول تاني. إعادة المحاولة مش هتفيد.

**4. Retry مع Exponential Backoff**
```ts
const delay = Math.min(1000 * 2 ** retries, 60000) + Math.random() * 1000;
```
الـ jitter (الجزء العشوائي) بيمنع إن كل الأجهزة تضرب السيرفر في نفس اللحظة.

## أهم نقطة: الـ Idempotency

لو الطلب وصل للسيرفر بس الرد ضاع، التطبيق هيعيد الإرسال والعملية تتكرر (طلب مكرر، دفع مرتين).

الحل إنك تبعت `Idempotency-Key` ثابت لكل طلب، وهو الـ `id` اللي اتولد وقت الإنشاء:
```ts
headers: { 'Idempotency-Key': item.id }
```
والسيرفر يحفظ المفاتيح اللي شافها، ولو جاله نفس المفتاح تاني يرجّع نفس النتيجة من غير ما ينفّذ تاني. من غير ده الحل كله مش آمن.

## تجربة المستخدم (UX)
- **Optimistic UI**: اعرض النتيجة فورًا واعتبر الطلب ناجح، وصحّح لو فشل.
- اعرض مؤشر واضح زي "في انتظار الإرسال" أو "بنحاول تاني".
- ادّي المستخدم طريقة يشوف الطلبات الفاشلة ويعيد المحاولة أو يلغيها.

## متى ترسل الطابور؟
- لما النت يرجع (NetInfo listener).
- لما التطبيق يرجع للـ foreground (`AppState`).
- عند فتح التطبيق.
- لو محتاج الإرسال والتطبيق في الخلفية: `react-native-background-fetch` أو `WorkManager` على Android. لكن iOS بيحدّ من ده.

## مكتبات جاهزة توفر عليك الشغل
- **TanStack Query** مع `persistQueryClient` و`onlineManager`: بيدعم mutations offline وإعادة تشغيلها تلقائيًا. دي أسرع طريقة لو بتستخدمه أصلًا.
- **Redux Offline** أو **redux-persist** مع middleware: لو عندك Redux.
- **WatermelonDB** مع sync: لو التطبيق offline-first بالكامل.

## قرارات لازم تاخدها
| السؤال | التوصية |
|---|---|
| كل الطلبات تتخزن؟ | لأ. الـ GET مش محتاج طابور، والـ mutations بس (POST/PUT/DELETE) |
| لو الطلب قديم قوي؟ | حط TTL، والطلبات المنتهية تتشال أو تطلب تأكيد |
| تعارض في البيانات (conflict)؟ | اعتمد على `updatedAt` أو version number، أو "آخر كاتب يكسب" |
| حساسية الطلب (دفع مثلًا)؟ | الأفضل متدخلوش في الطابور، واطلب نت وقت التنفيذ |
